# sg10 — Async collaboration polish

_Drafted 2026-08-18, against `develop` post-1.6.0, at the maker's explicit direction: polish the collaboration mechanics that already exist (remix, exquisite corpse chains, compilations), not real-time/live multiplayer editing. The app has zero live-sync infrastructure and is deliberately "client-first, server-optional" (`docs/sg2.md`) — live cursors/presence/conflict resolution were explicitly ruled out before this note was written, not something this note argues against. `sg.md`'s freeze holds: no new mechanics, no new routes. **§1 and §3 shipped.**_

Remix attribution itself is already good and already shipped (`docs/STATUS.md`: *"A remix names the original … on the editor and reader and hops back when that issue is still on the desk"*) — this note is about the corpse-chain and compilation experiences next to it, which never got the same pass.

## 1. The chain contributor never sees what page they're on

`server/routes/zines.ts:359–368`'s `GET .../chain` already computes and returns `turn: blocks.length` (`ChainPeekResponse`, `contract.ts:135`) — the page number this contribution will become. `useIssueSocial.ts:138–143` fetches this response and keeps only `res.previous`, discarding `res.turn`. `Preview.tsx:256–278`'s chain form shows the last 1–2 blocks and a bare `"EXQUISITE CORPSE · last page only"` chip — no indication of how far into the chain this is.

**Fix:** keep the number already being sent, render it:

```ts
// useIssueSocial.ts
const [chainTurn, setChainTurn] = useState<number | null>(null)
// in the chain-peek effect:
.then((res) => {
  setChainPrev(res.previous)
  setChainTurn(res.turn)
})
```

```tsx
// Preview.tsx
<div className="issue-chip">EXQUISITE CORPSE · page {social.chainTurn ?? '?'} · last page only</div>
```

Zero new mechanic — the number already crosses the wire on every peek, it just wasn't read.

**Shipped** exactly as above (`chainTurn` state + effect in `useIssueSocial.ts`, rendered in `Preview.tsx`'s chain chip). `e2e/reader.spec.ts`'s existing chain test (24) now also asserts the chip contains `page \d+`.

## 2. An unresolvable remix source is a dead end — flagged, not fixed

`Editor.tsx:417–427` and `Preview.tsx:244–254` both show `"remix of {title}"` with a link when `sourceOfRemix()` (`zine.ts:57`) finds the parent locally, and fall back to plain text — *"this is a remix. the original is not on this desk."* — with no link at all when it isn't loaded. Remix sources must be `published` at remix time (`server/routes/zines.ts:306`), so a bare `/z/:id` link (`issuePath` without the `?k=` share key) would resolve correctly in the common case — but `visibility` and `published` are independent fields, so a published-and-unlisted source would 404 or lock on a key-less link. Shipping a link that's right most of the time and silently wrong some of the time is worse than the current honest dead end.

**Not shipping a fix here.** The real fix is either fetching the source's `visibility`/`shareKey` before linking (a network call this component doesn't currently make) or accepting the occasional broken link — a product call, not a code call. Noting it so it isn't lost, same as sg6 did for its own "needs a design nod" item.

## 3. The compilation picker silently truncates at 8

`EditorMeta.tsx:93–114` filters to public drops and takes `.slice(0, 8)` with no count shown. A studio with more than 8 public issues has no way to know the picker isn't showing everything — the ninth-favorite issue just silently isn't offered, and there's nothing on screen to explain why.

**Fix:** one line when the cap is actually hit — no search, no pagination, no new mechanic, just honesty about what's on screen:

```tsx
{eligible.length > 8 ? <p className="serif">8 of {eligible.length} public issues shown.</p> : null}
```

**Shipped** (`compEligible` computed once in `EditorMeta.tsx`, reused for both the picker's `.slice(0, 8)` and this notice, so they can't drift apart).

## Noted, not proposed: every chain contribution is a sticker

`passCorpse()` (`useIssueSocial.ts:262–278`) always builds `createBlock('sticker', zine.vibe)` from the contributor's textarea — they never see the slash-command picker or any other block type, regardless of what they write. No planning note anywhere proposes or rejects this; it reads like a deliberate constraint (one page, one simple contribution, keep the chain's rules the same for everyone) rather than a bug. Not proposing a change — flagging it exists, since "improve collaboration" could plausibly mean this too, and it's worth a deliberate yes/no rather than silence.
